## 0. 目标、优先级与文档边界

**把本项目做成“一部玩家参与其中、人物记得往事、可以按日期翻阅的长篇小说”，不是带好感度条的通用聊天窗口，也不是必须点选项的数值 RPG。**

玩家控制当前剧本指定的主角；内置大曜仍唯一控制玄天华。模型负责叙事、环境、所有 NPC；程序负责已发生事实、状态、时序、人物认知、规则和存档。模型不能直接覆盖数据库或决定玩家意愿。

世界与人物以 `GAME_SETTING.md` 为准；技术与体验以本文件和 `API_PROVIDERS.md` 为准。最新的用户明确修改高于旧规格，但修改必须留下版本和迁移说明。`references/` 下的聊天样本永远不具有本局正史效力。

本方案对原规则的“小说模式”解释、未指定日期和朝局起始数值，均在第 15 节明确列为产品默认值，不伪装成用户原设定。

## 1. MVP 范围

首个可交付版本必须同时具备：小说正文阅读、自由输入与 NPC 交谈、OOC 分离、六名人物与双轨关系、基础事件调度、本地长期记忆、按日期和人物回看原文、多存档与分支、导入导出、三家 API 切换、可恢复的失败处理。

提供个人登录访问保护；不做公开社交、多人联机、复杂战争模拟、商城、立绘生成、语音、自动联网查史、云端向量数据库、后台无限自动推剧情。与服务断开时可阅读、搜索、导出明确下载的离线副本并保存未发输入；离线不能调用模型或修改服务端主存档。

不是预先写好六条路线让用户逐一解锁。玩家行为决定路径，NPC 有自己的目标、立场和有限知识；不保证全员忠诚，不保证必然恋爱。

## 2. 阅读与交互设计

### 2.1 主页面

移动端优先：手机和平板采用单栏小说阅读，紧凑顶部导航与日期场景、底部多行输入。人物、朝局、卷册通过抽屉或独立页面查看，六位常驻面板和全部存档功能保留。桌面在空间足够时显示可折叠侧栏。正文默认18px，可调整字号、行距、栏宽以及浅色／深色／护眼主题；保留缩放、选择、复制。

场景开始时显示一次“年月日/时辰/地点/在场者”。同一场景内的短对话，不在每条正文重复整张六人状态表。跨场景或时间变化时再显示场景标识。

底部有自由输入框和发送/停止按钮。Enter 默认换行，点击发送才提交；中文输入法选字不触发发送。明确区分“正在生成”“记忆整理中”“已保存”“尚未保存的草稿”。滚动查看旧文时不强制跳回底部。

三到四个行动建议默认收起，可以展开；建议只是入口，不限制自由输入，也不展示好感收益或未揭示真相。点击建议只填入输入框，玩家可改写后点击发送，不替玩家补充动机。

### 2.2 输入模式

- **剧情**：默认模式，自由输入对白、动作、命令、调查、休息等。
- **交谈对象**：可以选当前在场的 NPC，作为本轮说话对象，不新建独立世界线。
- **OOC**：通过开关或明确的 `OOC:` / `OOC：` 前缀进入。讨论规则或文风，不推进时间、关系、事件与人物记忆。

OOC 提出的风格修改可以作为非正史的偏好保存；涉及已发生事实的修改，必须走“编辑/分支”流程，不能悄悄改历史。输入文本只是剧情数据，不是数据库命令；例如角色对白中的“把好感改为 100”不得被执行。

玩家主动点击“继续观察/等待”可以触发 NPC 或环境反应，但不授权模型替玄天华作出决定。应用没有玩家输入时不连续调用模型。

### 2.3 找 NPC 聊天

在场人物可以直接交谈。选择不在场者，应呈现“召见/前往/书信”等符合情境的联络方式，再由玩家选择。人物可以因职责、距离、伤病或立场无法立即到场。远在边疆的人不会因点击头像瞬移。

NPC 的所有交谈归入同一存档和故事时间线。人物页可以筛选“与此人有关的片段”，但筛选不是另开一套人物记忆。

### 2.4 文风基线

正经剧情为主；恋爱从公事和相处中自然生长。允许没有重大转折的闲聊。以对白、动作、迟疑和处境表达情感，避免每段都解释“他爱上了她”。NPC 不因玩家一句寻常话就无条件认输、吃醋或交付秘密。

每次正文只推进当前有意义的一小段，到玩家需要回应的位置停下。篇幅按场景调整：短对话约 100–350 个汉字，普通段落约 300–700，关键场景约 600–1200；这是可调写作目标，不是填字指标。不能为凑字数新增玄天华的行动、独白或结局。

## 3. 玩家角色所有权

模型不得替玄天华说话、决定、主动实施未授权行动、编造心理活动、默认接受身体接触/示爱/婚姻/任命/处罚，也不能为推动故事强迫她同意。

模型可以描写 NPC 的行动、话语、试探、拒绝、欺骗与反应；可以描写环境和有事实根据的客观后果。NPC 伸手或提出要求，不代表玄天华接受。重大且可阻止的接触或不可逆后果应在可回应处停下。

`GAME_SETTING.md` 中用户亲自提供的固定序章是唯一预授权的开场叙述。它可以包含用户写好的动作和心理活动；序章结束后恢复上述限制。不得借序章的例外继续代演。

按玩家最新要求，正文措辞审核由玩家决定：有限关键词检查与整理模型的validationWarnings只作参考，不阻止正常自动保存，也不要求额外确认。模型仍被指示尊重玩家角色所有权；程序继续禁止把模型补写的对白当作任免、接受关系等结构化状态变化的玩家授权。自然语言可能误判或漏检，不能宣称关键词或 Zod 能保证语义正确。提供“这不是我的行动”“人物忘记前情”“时间跳太快”的纠错入口和草稿重写/已提交节点分支机制。

## 4. 设定、写作参考和本局事实隔离

资料分为三种不同命名空间：

| 类型 | 可以影响什么 | 不得影响什么 |
|---|---|---|
| `canon` | 世界背景、人物原设定、初始值、固定序章 | 不可自行替换为聊天样本里的结局 |
| `style_reference` | 提炼后的文风、对话节奏、叙述偏好 | 本局事实、人物认知、初始关系、必经剧情 |
| `save_history` | 对应存档、对应分支中已经正式采用的故事 | 其他分支或另一个新游戏 |

运行时默认只注入精简风格指南，不检索整段参考聊天。风格指南不得保留可被误当作既成事实的独有事件、告白、阴谋结论或具体玩家选择。

参考导入 UI 必须明确显示“仅参考写法，不导入剧情”。MVP 支持 TXT/MD 参考文本；不做长截图 OCR。只有通过本应用存档格式验证的数据可直接导入存档。外部自由聊天转成存档是后续单独功能，不偷偷自动完成。

基础设定存在服务器端，NPC 秘密和未揭示真相不能全部序列化进客户端人物卡。玩家界面默认只呈现已知信息；隐藏背景属于叙事管理信息，不是所有 NPC 共享的知识。

## 5. 时间、场景与日期索引

必须区分 `messageCount`、`sceneId`、`gameDate`、`createdAt`。一条消息不等于一场戏，更不等于一天。可以在同一个深夜交谈十几轮，只消耗合理的几分钟。

使用架空历法而非直接套现实日期：MVP 暂采用 12 月、每月 30 日的简化历法；开始日默认为凌月元年三月二十八日，界面可以显示“三月末”。此为可修改的产品默认值，原设定只指定“三月末”。新档高级设置显示此默认，不在幕后冒充用户设定。

`GameDate` 至少包括 `year:number`、`month:1..12`、`day:1..30`、`period`、`minuteOfDay`、`absoluteDay` 和 `calendarVersion`。年份和月份不能在类型中写成只能等于 1 或 3 的字面量。时辰显示由数值时间计算，保证两者一致。

起始为登基第三日；默认开局日确定后，相应计算登基日。起兵地点仍为未指定，使用 `null`，不得把“某地”当真实地名，也不擅自确定新地名。

小幅时间流逝可由引擎按当前行动和场景校验。跨日、长途移动、数小时工作、重大局势跳转需要玩家行为足以授权；不能用“天已经亮了”强行结束尚未回应的谈话。天气应按场景保持连续，不能每句聊天重抽一次。

历史页提供游戏日期范围、现实游玩日期范围、人物、地点、关键词、书签、分支筛选。对“某天之前”明确提供“不含当天/截至当天”选项，内部用排序键比较，不比较中文日期字符串。

历史阅读不会改变当前进度。查看某节点的人物状态时，读该节点的快照，不显示当前最新关系；生成“截至某日回顾”时，也只能使用该日期截点可见的故事。

## 6. 本地数据与版本模型

### 6.1 运行方式

采用统一 Next.js + TypeScript Web 应用。Node.js 服务调用云端模型并读写服务端 SQLite。默认 local 模式只监听 `127.0.0.1:3000`；显式配置 lan 或 public 模式后支持手机／平板浏览器访问。首版不做 APK、原生 iOS 或桌面安装包。

数据库放在明确、持久化的 `APP_DATA_DIR` 中，不放浏览器缓存、临时目录、构建产物或会被更新覆盖的目录。界面显示实际数据路径，提供备份与导出。

SQLite 主存档位于实际运行服务的电脑或持久服务器，不自动保存到手机。浏览器 IndexedDB 只保存阅读／输入状态、请求恢复信息和明确下载的离线副本；不是主存档架构替代。服务器模式须使用 HTTPS、个人登录、CSRF、Host/Origin 校验和接口／模型限流。不会默认上传旧档或自动部署。

### 6.2 基本数据对象

| 对象 | 关键内容 |
|---|---|
| `Project` | 基础设定版本、风格配置版本、日历规则版本 |
| `Save` | 存档标题、创建时间、初始配置、当前分支 |
| `Branch` | 分支 ID、父分支、分叉节点、当前 `headTurnId` |
| `Turn` | 已提交节点 ID、父节点 ID、玩家原文、正式正文、场景和时间、实际使用的 provider/model |
| `TurnDraft` | 请求 ID、基准节点、临时正文、提取结果、生成/校验/失败状态 |
| `StateSnapshot` | 节点提交后的地点、时间、人物关系、事件队列、世界状态和当前事实引用 |
| `FactEvent` | 结构化事实或声明的新增、修订、撤销，关联来源节点 |
| `NpcKnowledgeEvent` | 谁通过什么路径获知/误信什么，发生在哪个节点 |
| `Memory` | 人物记忆或重要片段索引，关联来源、类型和可见性 |
| `Summary` | 场景/章节摘要、覆盖的来源节点、生成截点、版本 |
| `Bookmark` | 玩家书签与非正史笔记 |
| `ProviderProfile` | 非敏感供应商配置及密钥引用，不包含明文密钥 |
| `OocMessage` | 与正式剧情隔离的规则讨论 |
| `Character` | 稳定 ID、saveId、seedKey、创建来源；六人以外使用服务端分配的 UUID |
| `CharacterEvent` | 来源节点、行动者、引文、前值与变化、游戏时间、可见范围及知情者 |
| `OfficeAssignment` | 实授／兼任／代理／差遣／荣誉，提议到离任的独立来源，实际权限 |
| `CharacterRelation` | 有向客观关系或主观态度，建立与结束来源，不默认对称 |
| `CharacterCorrection` | 更正类别、说明、原始来源、登记节点及可选修订分支 |

每个已提交回合保存结构化效果和状态快照。完整正文只存一次，不在每个快照内重复复制所有聊天历史。最初的数据规模用简单 SQLite 和索引解决，不先引入图数据库。

### 6.3 分支与可见性

采用不可变的已提交回合节点，每个节点指向 `parentTurnId`。新分支从指定旧节点创建，新的 `headTurnId` 起初指向那个节点。可见历史由当前 head 沿父节点追溯得到；缓存只是派生数据。

**不能只用 `branchId = 当前分支` 查询，也不能把父分支的所有后续节点全部继承。** 当前分支可以继承分叉前的节点，但不能看到分叉后的旧未来。

事实、NPC 认知、摘要、搜索索引和状态都遵循相同可见节点集合。摘要的来源有任何不在当前可见路径内，便不能注入上下文。旧分支中已撤销或替换的记忆，不应以全局覆盖方式修改另一分支。

“重新生成”若针对未提交草稿，只更换草稿；若针对已提交正文，必须从对应父节点另开分支。编辑过去的玩家输入或正文同理，不保留旧未来的关系增益与秘密。

## 7. 本地记忆设计

### 7.1 原文不可被摘要替代

完整玩家输入、正式正文和必要上下文永久保留，除非用户明确删除。摘要用于控制上下文长度，不替代原文。每条重要记忆都能点击跳回来源。

### 7.2 区分事实、说法和认知

`Memory/FactEvent` 至少区分：

- `confirmed_event`：实际发生并被采用的事件。
- `claim` / `rumor`：某人说过或流传某事，不代表某事为真。
- `belief` / `suspicion`：指定人物的看法，可能是错的。
- `promise` / `order`：承诺或命令；“命令下达”不等于“执行完成”。
- `intent`：打算做什么，不等于已经做了。
- `unresolved`：未结疑点。

每条记录包括稳定 ID、内容、主体、类型、来源回合、来源片段、游戏时间、实际记录时间、已知者/见证者、传播路径、是否已揭示、重要性和有效版本。模型给出的置信度仅供排查，不是证明。

例如第三镇粮耗异常应保存为“账面存在疑点，原因待查”；不能直接提取成“第三镇将领贪污”。玩家说“明日再查”，只能创建计划，不能落成“调查已结束”。

### 7.3 人物知识边界

沈彻不知道一场自己没有参加、也没有人转告的谈话。顾青崖怀疑女帝来历，不等于确定穿越。温回察觉异常，不等于能解释所有现代知识。

新人物知识必须有依据：本人在场、收到信件、被转告、主动调查获得线索，或原设定明确知晓。若 NPC 对未知事提出猜测，保存为带持有者的猜测，不扩散成公共事实。

对公开传闻也记录传播过程，不能因为后台存在秘密就让所有人自动知情。重要隐藏事实按需提供给叙事规划，不全部暴露到每位 NPC 的对白上下文。

### 7.4 每轮上下文选取

始终包含玩家角色所有权、最小世界背景、当前状态、当前在场/直接相关人物资料、当前事件与未决承诺。再加入当前场景最近约 8–12 轮、相关既往事件、上一场摘要及必要章节摘要。

先筛掉其他存档/分支/未来/参考资料，再做相关性排序。不能先全库搜索后“希望模型自己忽略”。检索按人物、别名、地点、任务和关键词进行；MVP 不依赖付费 embedding。

中文搜索至少支持参数化子串查询和人物别名。可加 SQLite FTS5 trigram；短于三个字符的名字要走普通子串查询或人物索引，不把默认英文分词当作完整中文检索方案。工程依据见 `SOURCES.md` [S9]。

上下文有预算，优先保留硬性设定、未决承诺和相关秘密。预算不足时压缩较远场景，不能静默删除玩家权限规则。UI 提供“本轮记忆预览”，显示将发送的资料及来源，不显示密钥或模型思考过程。

### 7.5 记忆纠错

玩家可以标记某条记忆错误、钉住重要记忆、编辑自己的笔记。修改结构化事实时保留审计记录和版本；已发生的事实变更通过明确的作者修订/新分支处理。不要用模型摘要覆盖用户纠正过的已确认内容。

## 8. 双轨关系与事件规则：小说模式

六位 NPC 的初始值严格见 `GAME_SETTING.md`。信任与好感分别保存，均限制 0–100。关系变化需要具体事件和可追溯依据，不是聊天一句就加分。

### 8.1 数值分配

模型只返回 `relationshipEvidence`：人物、事件类别、发生依据、正负倾向和原因。程序用配置表决定是否计入和实际幅度；不接受模型直接指定新分数或覆盖整个状态。

可采用普通有效事件 -2 到 +2、单场景普通事件净变化绝对值不超过 5 的初始限制；特殊重大事件另设明确规则。该幅度是设计默认值，可修改，不是用户原始数值规则。重复命令、重复询问、重复送礼不能依靠拆消息无限刷分。

没有合理证据时允许本轮零变化。采纳方案不必导致他人扣分；委派危险任务也不必自动让当事人更爱玩家。应考虑人物动机、是否知情、任务风险、是否获得支持和是否被尊重。

### 8.2 阈值和调度

保留严格阈值：好感 `>70`；信任 `>80 && 好感>60`；两名 NPC 各自好感 `>60`。不要误写成大于等于。

| 原机制 | 小说模式实现 |
|---|---|
| 好感 >70 的越界事件 | 生成该 NPC 的一次待发生事件，符合个性地表达越界倾向；不替玩家接受，也不默认发生亲密接触 |
| 信任 >80 且好感 >60 的脆弱事件 | 在安全、合理的相处场景展现；不在无关朝会上突然交底 |
| 两人好感 >60 的冲突 | 为人物对建立事件键，在有接触或知情条件时提出冲突；玩家可选择、调停、拒绝或延后，均有具体后果 |
| 连续三回合冷落 | 按三个“有接触机会却未回应的有效场景”计数；三条短回复不是三次冷落，在外地无法接触不计数 |
| 为同一 NPC 破例三次 | 统计三项不同、有实际后果的破例；存在见证或泄露路径后才发展为流言 |

这是对原规则的明确节奏调整。不得把“必须面对关系后果”实现成程序替玄天华站队，也不能无声删除触发条件。

事件状态至少有 `eligible/queued/introduced/resolved/cancelled`，并记录原因、触发节点、关联 NPC、优先级、去重键和冷却条件。一次性事件按 NPC 或无序人物对去重；主动找人事件可在冷却后再次成立。一次场景最多引入一个新的重要情感事件，紧急军政事件可以优先，未落地的情感事件仍留队列。

失败生成不能消耗事件 flag；只有对应正式剧情提交，才推进事件状态。已被拒绝或处理的事件不能每轮重复提问。

### 8.3 朝局

五项显示为威望、民心、军权、朝局稳定、财政状况，默认均为 0–100 的指标。财政状况指数不是实际库银；未来增加钱粮账本时必须使用独立字段和单位。具体起始值原设定未给出，见第 15 节。

战争、政治与感情有反馈，但不能为了增加困难无理由削弱玄天华或杀死重要 NPC。所有不可逆的大选择必须保留玩家决策点。

## 9. 回合引擎：正文和记忆分开生成，一起提交

为保证小说正文自然，并兼容不能稳定输出严格 JSON 的模型，MVP 使用两步生成：

```text
玩家输入
  -> 校验存档、模式、基准节点、请求 ID
  -> 固定本轮 provider/model/能力配置和当前状态版本
  -> 创建草稿，选取该分支可见上下文
  -> 生成小说正文（能够流式时显示为草稿）
  -> 提取事实、人物认知、关系依据、场景变化和建议行动
  -> JSON 解析 + Zod + 规则/来源/时序/权限校验
  -> 原子提交正文、事实、关系、事件、快照和分支 head
  -> 标记“已保存”，允许下一轮
```

普通剧情轮通常有一次正文请求和一次结构化整理请求。默认两者使用同一供应商/模型；高级设置可指定另一个整理模型，但不能偷偷新增供应商或费用。场景/章节摘要按需生成并缓存，不每句话都再做一轮大摘要。OOC 不走剧情记忆提取；本地显示固定序章也不消耗 API。

### 9.1 结构化结果

正文是可读文本，不强制模型把整篇小说装进 JSON。正文生成后按段落建立本地 `blockId`。整理器输出的 JSON 只包含建议，不拥有数据库写权限。

建议字段：`sceneProposal`、`eventProposals`、`knowledgeProposals`、`relationshipEvidence`、`pendingThreads`、`suggestedActions`、`validationWarnings`。每项建议引用玩家输入或正文 `blockId` 以及短原文证据；证据必须真实存在。

只允许白名单类型和人物 ID，限制数量、文本长度与数组大小。不要提供任意 JSON Patch、SQL、文件路径或函数执行能力。未知属性拒绝，数值范围校验，发生顺序和现场人数校验，记录被拒绝的原因。

### 9.2 一致性与失败处理

结构合法不等于事实正确。整理器不能根据一段计划补写已经发生的结果。正文声称发生了不被引擎允许的重大变化时，不能仅拒绝数据更新却把矛盾正文正式保存；应修正/重写草稿并重新提取，或保留为未提交草稿交给用户处理。

JSON 格式错误最多进行一次自动修复；修复仅针对结构，不得新增情节。仍失败则保留正文草稿，提示“记忆未写入”，允许只重试整理步骤，不必付费重写整篇。状态和事件保持原样，不能在未完成记忆提交时继续依赖半成品剧情。

网络失败、限流、截断、空输出、取消、拒绝生成均不产生正式故事或好感变化。用户能选择保留草稿、重试或放弃；错误信息不写成 NPC 台词。

### 9.3 幂等、并发、事务

每个请求携带 `clientRequestId`、`saveId`、`branchId`、`expectedHeadTurnId`。同一请求重复提交只得到同一结果，不重复加分；一个分支同一时刻最多一个有效生成流程。

网络调用不放在长期持有的 SQLite 写事务里。最后提交时再次校验 head 和版本，使用事务写入全部正式数据。另一窗口已推进则返回冲突并保留草稿，不把旧状态的结果覆盖新状态。

中断后重新打开应用，可以看到未完成草稿与已提交节点。取消与提交竞态以服务器状态为准：已提交不能伪称已撤销，需走明确分支/回退流程。迁移、备份与恢复不能破坏已提交节点链。

流式文本也不是提前确认的事实。重试不直接把新输出拼到旧文本尾部。传回的 `reasoning_content`、thought 等推理字段不显示为正文、不进入人物记忆、不作为故事依据。

## 10. API 适配要求

第一版必须有 `SiliconFlowProvider`、`DeepSeekProvider`、`GoogleGemmaProvider` 和用于离线测试的 `MockProvider`。三家都有实际实现，不能仅做下拉框。

硅基流动和 DeepSeek 可以共享 Chat Completions 传输代码，但仍有各自的参数与错误映射。Google 采用 Gemini Developer API 原生 `generateContent` 路径；预设模型为 `gemma-4-26b-a4b-it`，不是 Gemini 型号，也不是 OpenRouter 名字。端点和来源见 `API_PROVIDERS.md`。

能力按 `供应商 + endpoint + model` 记录，不能只按厂商标一个“全支持”。系统消息、结构化输出、流式和思考参数分别处理；只发送已支持参数。未知能力采用保守文本路径与本地校验，不自动换模型。

设置页提供供应商、模型列表/手填 ID、连接测试、可用参数、超时、正文长度/输出限制、能力状态与最近错误。切换后沿用当前存档和本地历史；只改变新请求，不能调用模型重置人物。实际生成供应商和模型写入回合元数据便于排查。

## 11. 隐私与密钥

所有云端模型请求由实际部署的服务端发出。生产浏览器代码不得硬编码密钥，不放 `NEXT_PUBLIC_*`、localStorage、IndexedDB、导出文件或普通日志。Google 官方对服务端代理和密钥保密的要求见 `SOURCES.md` [S6]。

本地 `.env.local` 是一种可选持久化方式，明确告知其为本机明文配置，不宣称加密；必须加入 `.gitignore`。设置页输入的 Key 在浏览器表单中短暂存在是必要的，提交本地服务后清空；默认只保存在服务器进程内存，重启需重新输入。

MVP 不实现自制“把加密密钥也放旁边”的伪加密保险箱。可后续接操作系统凭据库。数据库只存密钥引用或配置是否存在，不存明文。

默认三个官方主机白名单，不提供任意 URL 代理。若后续允许自定义 Base URL，要二次确认数据发送目的地、限制协议、处理重定向和内网地址风险；修改目的地不得自动携带原供应商密钥。

本机服务也校验 Host/Origin、限制 CORS 和写请求，使用会话/CSRF 防护；不因为监听 localhost 就开放所有跨站请求。渲染 Markdown 禁止原始 HTML/脚本，链接与导入文件要校验，ZIP 导入防路径穿越、超大解压和不支持的 schemaVersion。

UI 明示“主存档保存在服务端；本轮选定内容发送到 X”，离线时明示浏览器副本。自动切换供应商默认关闭。导出默认排除密钥、思考字段、未提交草稿和原始网络调试日志。

## 12. 存档、回看、备份和导出

自动保存发生在每次原子提交后；手动存档槽保存当前分支 head 和名称，不必重复复制整本小说。支持新游戏、读取、重命名、明确确认后删除和从某节点另开分支。

导出分两类：

| 导出 | 内容 |
|---|---|
| 阅读版 TXT/MD | 指定分支、指定日期范围的玩家原文与正式正文，保留顺序、分场景标题，不编造过渡或重写玩家 |
| 可恢复存档 JSON/ZIP | schemaVersion、设定版本、日历规则、节点链、状态、事实、人物记忆、书签及完整性校验；不带密钥 |

导入先校验并创建新存档，不默认覆盖已有内容。针对错误版本、损坏文件和来源节点缺失给出明确提示。备份采用 SQLite 安全快照/在线备份方式，不在 WAL 活跃时只复制主数据库文件；依据见 `SOURCES.md` [S8]。

保留有限数量自动备份，例如最近 10 个轮换备份；用户可以另存独立备份。迁移前备份，不以“修复数据库”为由清空已有游戏。

## 13. 工程实现建议

采用一个仓库、一套明确技术栈：Next.js + TypeScript + React + Tailwind CSS；Node.js Route Handlers；SQLite + `better-sqlite3`；Zod；Vitest；Playwright。数据库访问通过 Repository 模块和版本化 SQL 迁移封装，不再并行引入 Prisma 或其他数据库系统。

这里是建议的工程选择，不是用户强制的语言偏好。开发时核对稳定兼容版本并锁定依赖；SQLite 相关路由使用 Node.js runtime，不使用 Edge runtime。运行时区别的官方依据见 `SOURCES.md` [S7]。

Google 适配器使用官方 `@google/genai`；另外两家可用服务端 `fetch` 实现 Chat Completions 与 SSE，或使用兼容 SDK，但不要因此要求用户提供 OpenAI API Key。游戏运行时不需要另一个托管 Agent 服务。

```text
app/
  page.tsx
  play/[saveId]/page.tsx
  history/[saveId]/page.tsx

  settings/page.tsx

  api/saves/...

src/
  domain/          # 类型、关系规则、日期、事件和纯函数 reducer
  engine/          # 回合编排、校验、草稿、提交
  memory/          # 分支可见性、检索、摘要、来源追踪
  llm/             # provider interface、各家 adapter、prompt、extractor
  storage/         # SQLite repository、migrations、备份
  security/        # 凭据引用、日志脱敏、输入与导入校验
  server/          # API 应用服务
```

纯规则模块不依赖 React、数据库或具体供应商。UI 不直接发起上游模型请求。Prompt、规则、设定、数据库结构分别版本化。

## 14. 开发阶段与交付

| 阶段 | 实现内容 | 退出条件 |
|---|---|---|

| M3 | 三家真实 adapter、模型选择、能力降级与连接测试 | 每家都有契约测试；提供凭据时可运行显式 smoke test |

完整验收见 `ACCEPTANCE.md`。最后交付安装启动步骤、数据目录、密钥配置、备份恢复方法、如何添加人物/事件/provider、已知限制和实际运行过的测试命令。

## 16. 动态人物增量（2026-09-27）

详见 `DYNAMIC_CHARACTERS_ADDENDUM.md`。六位模板只用于开局与原有路线；`SeedId` 仍约束六人的数值机制，运行时 `CharacterId` 为种子 ID 或服务端 UUID，事实、在场、认知、交谈目标允许动态人物。无关群体不建独立档案，年龄、身世和动机允许未知，不添加测试示例为默认剧情。

共享人物主记录只保存稳定元数据。姓名、别名、身份、背景、性格、动机、势力、处境和路线配置从当前节点的祖先事件派生。源事件与原文不可变，历史称呼不批量替换。`draftRef` 使用本请求内引用，服务端依据 saveId/requestId/ref 分配稳定 ID，与名称官职无关；重复请求复用结果。同名、同官职与未解析称呼只列出候选，纠错留审计并可从来源前分支，不自动合并。

现有事实整理 Schema 增加可选 `proposedCharacterCreations`、`proposedCharacterChanges`、`proposedOfficeChanges`、`proposedRelationshipChanges`、`proposedKnowledgeChanges` 与 `unresolvedMentions`。旧结果可省略空数组；叙事出现明确新人物／任职变化但缺少对应记录时，有限语义检查会拦下草稿。每项提案须有本轮引文，职务按稳定 assignment ID 记录 `proposed → ordered → active → arrived → ended`，到任为独立步骤，允许直接从有效职位离任。新命令不得覆盖另一人的任职记录；升迁或罢免不自动加分、改地点或清除承诺。

女帝任免、封赏、处罚必须来自玩家明确行动或当前祖先路径内的明确授权；不能截取否定或假设中的片段冒充命令。NPC 自主任用须有有效职权或范围明确的授权，辞职需本人行动及来源。荣誉称号不附加权限。未知制度细节不凭官职长度推断。人物事件保存来源、行动者、理由与前值，职务、阵营和位置互相独立。

客观关系与主观态度分别存有向边，无反向态度推断。身份确认、自称、传闻和怀疑分开；消息传播须有在场或实际收到／调查路径。获知事件指向原信息事件，仅更新接收者的知识。玩家人物 API、普通存档 API、草稿和上下文预览都在服务器端裁剪隐藏人物信息；不会把秘密前值或内部动机放入普通响应。搜索只检索当前节点公开投影。完整恢复备份明确含隐藏数据，阅读版只保留原文。

上下文优先取在场、点名、任务相关人物及必要关系，详细人物默认软预算12（可调6–40）；必要在场／点名可超过软预算，世界人物总量不受此值限制。提供精简人物索引，避免每轮全量传所有履历。当前职务以重放记录为准；新的身份／职务变更后，早于变更的摘要在上下文中被剔除并由当前记录重建，原摘要和旧正文保留为历史。

人物创建、履历、知识、关系、事实、正文和分支 head 在原有一次 SQLite 提交中完成，没有第三次必需模型调用。失败留草稿，事务异常不遗留孤儿人物。SQLite v2 增加 `characters`、`character_events`、`character_corrections`；v1升级前 `VACUUM INTO` 快照，DDL与种子索引事务提交，旧节点 payload 不修改。缺少旧任职细节标未知，不伪造任命。JSON v2 包含新引用及纠错、支持导入 v1；导入做来源和祖先路径校验并创建新档。

移动端保留六人侧栏，增加独立人物簿，列表搜索／分组、单列详情、履历到原文和“当时档案”入口；手机可返回列表。关注存为 UI 设置，不能增减信任或触发召见。新人物恋爱默认关闭，不展示种子数值条；仅已知成年且明确确认才能开放，写零模型调用的分支配置节点，不更改剧情时间或原记忆。纠错类别包括身份、职务、认知与履历，登记节点晚于回看节点时不展示更正。

本版不提供人物自动合并、全官制模拟器或自动双向云同步；支持显式下载到浏览器的离线副本。自然语言校验只是可测试的防错规则，误判与漏判仍需草稿修订、审计纠错和授权后的人工叙事验收。四阶段实现与运行记录分别见 `IMPLEMENTATION_PLAN.md`、`VERIFICATION.md`。

### 草稿整理失败恢复（2026-09-28）

草稿保留正文配置与整理配置快照。重试默认保留原模型，同一配置同一模型的等待预算可刷新；用户可在草稿处明确选择另一份已保存的整理配置和本次5–300秒的总请求期限。选择展示供应商、模型与计费提示，不自动换服务，不重新生成完整正文，不改变全局选择。修订正文的确认按钮显示并采用当前整理配置。正文措辞检查仅作提示，完整结束标志不代表结构化事实及来源已验证。

新增可选的人工作者整理路径：仅针对本场交流、明确行动及登场，由玩家核对正文、在场名单、逐字来源和至少一项记忆，可登记普通新配角。确认后服务端仍执行来源、玩家权限、角色可见性、知情范围、出入场等校验；不推进时间地点、不增加关系分数、不生成固定行动建议。女帝任免、身份揭露、关系履历与远方传播不由简要表单处理；已有这类提案不被静默丢弃。新人物与事实仍采用原动态系统的稳定ID与来源节点。

正常生成默认自动整理记忆、校验并原子保存，无逐节确认、记忆表单或额外保存动作。进行中显示“随后自动保存”，失败才提供一键重试自动保存。手工表单收纳到“手动整理记忆（高级补救）”，填写后点击保存即代表采用该正文，不再要求另勾核对确认。按钮旁实时列出缺少的正文或记忆内容，零项和空白记忆不能提交；添加记忆后定位到新增输入框。服务端来源与玩家权限校验保持不变，不把记忆失败或未完整接收的内容伪装成正式剧情。

已保存段落直接提供“修改”入口，支持编辑正文或改写玩家输入。在同一个编辑窗口点一次提交，自动从原节父节点建立命名修订分支，重新整理并保存；不先弹分支命名／确认窗口。取消编辑不发请求、不建分支。原文、原分支未来与记忆完整保留，新分支只读父节点以前的状态。固定序章和纯人物配置记录不在正文编辑范围内。

正文诊断使用有限规则返回原句与UTF-16定位范围，编辑器支持定位；这些提示不禁用保存或仅重试记忆的按钮，不触发强制重写。已保存段落的“本节提示”默认收起，正文和提示分别显示，原文保持完整。固定序章免于提示。模型validationWarnings不作为否决权，仅记录固定参考说明，不能将其中可能含有秘密的原始文字返回前端。

完整且失败／停止的剧情草稿仍可显式选择“自动修正并保存”，作为折叠的可选工具。使用当前正文与整理配置，只执行一次修正再走原事务。修正结果仍有措辞提示时允许正常保存；网络、Schema、来源或重要状态校验失败时保留草稿。可选bodyRepair字段保留原稿与候选，无数据库迁移、不自动循环或后台重放。

### 玩家决定正文与整理容错（2026-10-01）

本次按用户明确要求替代早期“正文关键词命中即阻止保存”的交互，不改世界、序章、六人设定、玩家任免授权或人物认知规则。模型文字建议不具有程序审批权，生成完整且记忆／状态通过校验后默认提交，玩家可随时修订分支。

在既有校验前，仅对可选摘要字段做确定性规范化，保留原模型提案供排查：天气为空、缩写既有描述或没有新原文依据时保留此前天气；eventProposals不对应已有系统事件key时不触发队列，普通剧情仍由带来源facts留存；没有对应既有事项或facts.content的pendingThreads文本不另建待办，由原有规则从有来源的计划／命令／承诺／疑点补齐。已知事件的触发条件、事实引文、角色登记、身份履历、任免授权、认知传播、关系数值和时间地点仍走原校验，不把失败整体吞掉，也不丢弃复杂人物提案。每项规范化以固定说明记录于effects.diagnostics，公开接口只允许这些固定说明，不暴露后台原始警告。

旧失败草稿若已有完整正文和Schema有效整理结果，提供“保存这段剧情”。POST drafts/:id/save提交草稿版本；服务端在一个SQLite事务里复核状态、版本和head，使用既有extraction重新规范化／校验并提交。此路径不调用供应商、不改正文、不增加请求计数，不需要填记忆或额外确认。没有整理结果、正文不完整、在途请求、旧版本或移动的head拒绝，重复已提交ID返回原结果，写入错误回滚整个事务。公开草稿只给localSaveRevision，不把隐藏extraction下发客户端。正常新生成自动处理同样问题，无须再点该恢复按钮。无架构迁移；旧节点及正文不回写。

审阅GET只返回原节点公开人物、正文与SHA-256草稿版本；POST在同一SQLite事务里复查版本与分支head、验证、恢复已停止草稿并提交全部正文／记忆／人物／状态。旧表单、并发生成、变化的head会拒绝；重复提交返回原结果。任一步异常均回滚，原草稿保留。正式节点可选字段`memorySource=local-review`记录整理来源，保留原正文模型和实际请求次数，导入导出兼容。无需数据库迁移。

“让门外的人进来／让对方进来”可授权一位正文明确识别且实际进入的来人，不要求玩家预先知道姓名；不授权多位来人，不把假设、否定或传闻视为命令，也不允许远方人物瞬移。有限自然语言检查不替代人工叙事验收。

### 手机连续使用与离线更新补强（2026-10-01）

切换卷册／分支前立即写入未发送输入、OOC和交谈对象，再读取目标分支；防抖计时器未到期也不能丢失最后输入。异步读取带递增序号，较早的请求迟到不能替换后来选择的卷册。阅读锚点和章节页仍按存档／分支隔离。现有20节分页限制正文渲染，初次API仍传回整条可见分支；超大存档的网络分页和十万节点性能不在已验证结果中。

安装事件和Service Worker注册由应用根组件统一管理，在故事页收到beforeinstallprompt后保留入口，设置页反复开关不丢事件。独立显示模式和iOS standalone标志用于识别已安装打开状态。只有用户主动更新才激活等待中的版本并刷新，生成中、结果未知、输入／正文编辑中及下载副本期间禁用更新；刷新前再次保存输入。旧页面使用的上一版静态资源继续从应用壳缓存提供，API和密钥仍不进缓存。

离线下载先核对格式版本、存档ID、SHA-256版本字段、分支数量、完整父节点路径、原文一致性和每节点人物簿来源，再在一个IndexedDB事务中比较并替换。较早下载晚到不覆盖较新副本；服务标识改变时保留旧副本并提示先导出再显式移除。下载时间只用于同来源下载先后保护，不用来合并剧情或写回服务器；云端主档并发仍依据expectedHeadTurnId。下载范围验证不是重新解释剧情事实或浏览器端的身份授权。

回归包含Windows Edge视口、Playwright WebKit手机参数与Chromium安卓参数；均归类为桌面引擎模拟。真实iOS Safari与Android Chrome的IME候选、系统键盘、地址栏、安全区、PWA安装、锁屏和文件分享需真机记录。实现和测试不触发真实模型、历史上传或服务器购买。

移动网络下，旧卷册的生成响应、状态恢复与后台完成轮询不得抢占正在打开的新卷册；原请求ID仍留在原分支用于之后查询恢复。在线和离线TXT／Markdown复用同一只读格式化函数，保留正文原文，略过纯人物配置节点。设置页切换到当前配置列表里缺失的供应商时，使用既有供应商默认配置作为表单初值；Google仍为原生Gemma适配器和gemma-4-26b-a4b-it，不迁移或覆盖既有记录。


## 20. 手机独立游玩与生产架构评估（2026-10-01）

本节依据 PRODUCTION_ARCHITECTURE_ADDENDUM.md，更新部署要求，不改动序章、人物、关系、认知与玩家控制权。localhost / LAN 仅用于开发和本机使用；新增生产目标必须在个人电脑完全关闭时仍可通过 HTTPS 登录、续写和持久保存。原持久服务器 SQLite 说明不能直接视为新生产方案。

先完成 Sites Compatibility Spike，再按实测选择 A（Sites 全部关键能力）、B（Sites 前端加唯一权威外部后端／PostgreSQL）或 C（标准 Next.js／PostgreSQL）。2026-10-01 至02已实际发布合成站，并按用户要求设为公开。云端内部原规则回合、D1事务与更新保档通过；当前入口Cloudflare拦截，45秒后台任务未完成。本轮选择C作为下一阶段生产方向；正式后端尚未部署，不能把测试站视为正式游戏。详情见根目录 SITES_COMPATIBILITY_REPORT.md。

部署边界使用 StorageAdapter、SecretProvider、AuthProvider、JobRunner，以及既有 LLMProvider。记录适配器必须按 ownerId 隔离、比较 revision，并保证所有写入原子成功或失败；模型和人物规则保持纯业务模块。主应用当前仓库／调度仍为 SQLite／进程内实现，不能把新增契约误称为完整生产迁移。

GenerationJob 的 queued → building_context → generating_story → extracting_memory → validating → committing → completed 状态与 failed / cancelled 持久保存。记录请求ID、分支／期望头、供应商模型、时间、正文草稿和错误类别。同 clientRequestId 返回原 Job／Turn；状态查询不调度，重启后不自动重放上游结果不明的生成。正式执行器需要平台持久队列或数据库租约 worker，并在实际平台测得后接入。验证用 waitUntil 调度不是生产执行器。

正式提交同时更新正文、人物、履历、记忆、知识、关系、世界、快照、头节点及 Job。旧头／过期版本拒绝，失败保存草稿，结构化任免与知识仍需真实来源。保存、关系加分、新人物不因刷新／重复请求而重复。前端只读取当前节点可见投影；授权用户完整备份仍不能含 Key、密码、Session 或 reasoning。

SQLite 保留用于开发／测试及旧档。生产的存储与迁移需在架构选择后实现：从已备份旧库只读迁出，完整保留 ID、来源和分支，导入新命名空间，逐项核对后切换，不覆盖已有库。手机 IndexedDB 仍只是带 serverRevision / headTurnId 的副本，不会成为独立权威存档。

正式公网所有游戏接口必须认证、授权、跨站限制、限流、参数校验与日志脱敏。Secrets 仅存在服务端，Google 默认原生 Gemma 不变。合成测试发布与公开、真实 Key／模型测试、已有历史上传、付费资源和正式上线按对应授权进行。真机、平台强制重启、锁屏恢复与关电脑访问尚未验收，不能用本地构建或视口测试替代。

公开站点允许访问页面，不允许匿名读取或修改任何人的存档；登录用户仍按稳定用户标识隔离。合成站公开已获明确授权，不等于正式用户历史或密钥上传授权。更新保档已在测试D1和不同发布版本间验证，平台强制重启、真实手机锁屏和正式库迁移仍未验证。原waitUntil执行器仅用于验证，45秒失败保留原任务／输入，状态查询与同ID重提不重放生成；下一阶段改为持久worker，不改变剧情规则。

## 21. 通用 Scenario 引擎（2026-10-02）

### 21.1 Engine、Scenario 与 Save

Engine 管模型适配、请求任务、人物来源、记忆、数值校验、事务、分支、历史、阅读、PWA 和访问保护。Scenario 管世界、玩家、种子人物、开局、文风、日历、数值定义、声明式触发规则、Lore、地点、势力及安全 UI 配置。Save 管这一局实际发生的事。核心模块不再导入固定六人表补缺设定；缺少绑定快照必须报错，不能降级成大曜。

唯一正式内置包为 `packages/dayao_empress/`，原始大曜内容和规则不变。其他包从剧本库创建／导入；现代侦探测试夹具只由测试代码引用。剧本包不是完整 RPG、脚本插件或服务器程序。

### 21.2 包格式、草稿与安装

Package Schema 1 / Engine Schema 1，实际 JSON Schema 位于根目录 `packages/scenario.schema.json`。必需 manifest、world、player、rules、opening、style；人物卡在 characters，calendar、lore、references、assets 可选。导出含 scenario-data.json，以保存初始场景、主角候选、地点、势力及 UI。稳定 packageId 不随标题变化，版本为语义版本，同 ID／版本不可被不同内容覆盖。

手动向导允许长文本世界、玩家、人物、开局、自然语言规则和文风，不要求 JSON；高级模式提供完整配置。ZIP 和 TXT／MD 都先校验、展示预览，再经哈希确认安装。AI 整理保留原文并显示转换结果，关键字符串必须有原文依据，未知留空，整理不自动安装。真实网络整理需明确选择；无 Key 时使用 Mock。复制内置包分配新 ID；编辑普通包创建新版本，保存既有稳定人物 ID 和未改字段。

ZIP 仅在内存流式解码，限制压缩 4 MiB、展开 12 MiB、256 项、单文本 512 KiB／图片 2 MiB；校验目录、路径、重复项、CRC、UTF-8、图片签名及 Schema。拒绝脚本、HTML、SQL、可执行文件、符号链接、绝对／远程路径和 ZIP Slip。Markdown 作为文字展示，不执行 HTML。包不能注入 CSS、JS、文件、数据库或联网工具。

### 21.3 玩家、开局、人物与可选系统

玩家模式 fixed／customizable／selectable。每局的姓名、人设和选择写入局内快照，模板不改。PlayerOwnershipPolicy 默认独占控制，禁止补对白、决定、主动行动和内心；正文提示交玩家判断，结构化任免、知识和状态变化仍需来源授权。

fixed 原样显示作者开场，只在开场授权作者写定的玩家行为。generated_from_seed 先创建 pending 存档，玩家点击后以正常任务生成第一幕并原子提交。interactive_setup 要求自定义／候选主角，先填写再开始，不与 fixed 主角混用。

所有角色使用稳定 ID。种子由包提供，运行时个体仍走动态登记、提案、校验和事件重放。新配角默认不开放恋爱和数值；明确配置可提高重要性、打开剧本允许的数值和成年人物路线。关系、记忆与承诺不因改名或换职位重置；同名／同官职不合并。任职通用为 RoleAssignment，保留旧 offices 字段兼容，以 roleType 表达 office、job、rank、title、organization_role、temporary_role。人物地点有 locationId，势力有稳定定义；临时地点和 StoryThread 都携带来源节点和逐字证据。

人物数值为 `relationships[characterId].values[statKey]`，世界数值为 `worldStats[statKey]`。定义包括名称、范围、初值、单次幅度和场景上限；人物可 scenario_default、explicit 仅部分数值或 disabled。关闭关系系统不显示空信任／好感，客观关系与单向态度仍独立。数值改变受原文、幅度、去重和知情约束；阈值事件由安全 all／any 比较表达式、范围、冷却和路线策略执行，不执行任意代码。

CalendarDefinition 支持公历、不同月长的架空历、相对天数和无时间。消息／场景／日期始终分开。StoryThread 类别由包声明；不同世界可以使用案件、任务、承诺和其他类型。既有大曜旧字段仅由 legacy 适配器转换。

### 21.4 Prompt 与公开信息

严格五层：1 引擎权限和控制策略，2 当前快照世界／人物模板／风格／相关 Lore，3 祖先节点事实、记忆、知识及人物状态，4 当前场景，5 末条 user 玩家原文。风格偏好留在第 2 层，当前输入不在系统层重复。字符预算计算完整序列化内容与原文，删减低优先材料，预算不足时明确失败。

Lore 按在场／目标人物、地点、势力、任务与关键词选择最多八条。references 不成为事实或历史，不把原参考聊天直接作为上下文。模型可按选中人物读取必要作者背景，但普通 API、人物簿、上下文预览和历史状态仅返回当时玩家可见投影。完整恢复导出和明确下载的恢复副本单独保存隐藏状态，不用来渲染人物卡。

### 21.5 版本、分支与旧档

数据库 v3 增加 scenario_packages、scenario_snapshots、character_stats、world_stats。迁移前在线备份，事务内将旧 court 和双轨值转为 key/value，保留正文、六位 ID、来源引用、分支和现有数值。主库不迁目录。JSON v3 包含快照；v1／v2 先校验原 checksum 再转换。旧 IndexedDB 副本只读兼容，不静默写回服务器。

Save 记录 scenarioPackageId、scenarioVersion、scenarioSnapshotHash；节点绑定自己的快照。新版本安装不会改变旧局。显式升级先展示差异，仅元数据／风格／Lore 等安全变动可提交配置节点；人物、人设、规则、开场和历法变化拒绝，旧快照继续可用。配置不推进时间和数值，同请求去重，旧节点／旧分支保留原快照。任何存档仍引用包时阻止删除，删除模板不删除历史。

### 21.6 手机、主题、导出和交付边界

导航包含剧本库、故事、往事、人物簿、设置；六位面板只由大曜的 pinnedCharacters 指定。人物簿支持主要、剧情、近期、离场、关注及自定义分类，分类仅为 UI 设置。场景标签和数值名称来自包。主题只允许安全 accent、backgroundPreset、fontPreset、包内封面；玩家阅读偏好优先，保留放大、复制、18px 默认字号与触屏控件。

剧本 ZIP 导出作者模板；存档 JSON 导出实际剧情及全部快照，TXT／MD 导出采用的原文。移动文件选择器、离线阅读、请求恢复、版本冲突、密钥隔离和个人登录保持原协议。手机离线不能生成或安装服务器剧本。

Phase 1–9 与本机／浏览器模拟验收已实施，实际命令结果记录在根目录 SCENARIO_DELIVERY_REPORT.md，操作和 15 项完成报告在 SCENARIO_GUIDE.md。公网仍遵循第 20 节的生产目标；本轮未把 SQLite 本机构建视为 PostgreSQL、持久 worker 或关电脑后的生产验收，也未上传已有存档、真实 Key 或发布新的正式站点。真机仍需人工验证。
