# 新增重大需求：将“大曜女帝”改造为通用互动小说 / 文字冒险引擎

现有“大曜女帝”项目不再只服务一个固定世界观。

新的产品目标：

将项目改造成一个可以自由导入：

- 世界背景
- 玩家角色人设
- NPC 人设
- 开局剧情
- 时间规则
- 数值系统
- 人物关系规则
- 叙事风格
- 特殊事件规则

的通用 AI 互动小说软件。

现有“大曜女帝”不得删除。

它应迁移成一个标准 Scenario Package，
作为软件内置的第一个完整示例剧本：

dayao_empress

核心游戏引擎不得再硬编码：

- 大曜
- 玄天华
- 沈彻
- 顾青崖
- 谢兰舟
- 裴听雪
- 拓跋野
- 温回
- 信任度
- 好感度
- 凌月元年
- 女帝
- 朝局五项数值

这些必须全部从当前安装的剧本包读取。


==================================================
一、产品结构
==================================================

最终软件结构：

通用互动小说引擎
        ↓
安装 / 导入 Scenario Package
        ↓
选择剧本
        ↓
创建新存档
        ↓
开始游玩


例如：

Scenario Package A：
大曜女帝

Scenario Package B：
现代校园

Scenario Package C：
末日生存

Scenario Package D：
西幻宫廷

Scenario Package E：
用户自己创建的世界


所有剧本共用：

- 小说阅读 UI
- AI Provider
- Memory Engine
- Character Engine
- History
- Branch
- Save
- GenerationJob
- PWA
- 公网部署
- 手机 UI
- 导入导出

但人物、世界、规则和开局互相独立。

==================================================
三、manifest
==================================================

每个剧本包使用稳定 packageId。

例如：

{
  "schemaVersion": 1,
  "packageId": "dayao_empress",
  "version": "1.0.0",
  "title": "大曜女帝",
  "description": "...",
  "author": "...",
  "language": "zh-CN"
}


同时声明：

- 玩家角色模式
- 是否允许动态人物
- 是否包含关系系统
- 是否包含时间系统
- 是否包含恋爱机制
- 是否允许剧情分支
- 默认叙事风格
- 默认模型建议
- 所需 Engine Schema Version


packageId 不因标题修改而变化。


==================================================
四、玩家角色不能写死
==================================================

当前程序中的“玄天华”必须迁移为：

PlayerCharacterDefinition


例如：

{
  "id": "player",
  "name": "玄天华",
  "description": "...",
  "playerOwnership": {
    "exclusiveControl": true,
    "allowNarratorDialogue": false,
    "allowNarratorDecision": false,
    "allowNarratorInnerThought": false
  }
}


不同剧本可以有不同玩家角色。

例如：

剧本 A：
固定玩家角色玄天华

剧本 B：
用户输入姓名和人设

剧本 C：
开局时从三个主人公中选择

因此支持：

fixed
customizable
selectable

三种 Player Character 模式。


==================================================
五、玩家控制权规则也要剧本化
==================================================

“大曜女帝”中的：

模型不得替玄天华：

- 说话
- 作决定
- 主动行动
- 编造心理活动

应成为：

PlayerOwnershipPolicy

由剧本定义。

但软件提供安全默认值：

exclusiveControl = true

即默认不允许 AI 替玩家角色做重大决定。


==================================================
六、人物系统通用化
==================================================

Character 不再假定：

“NPC 一定有信任度 + 好感度”。

人物基础结构：

Character

stableId
displayName
aliases
description
appearance
personality
background
goals
motivations
faction
initialLocation
importance
romancePolicy
knowledge
relationships
customAttributes


角色可以：

- 没有恋爱系统
- 只有信任
- 有好感和信任
- 有恐惧、忠诚、敌意等自定义属性

不得把：

trust
affection

写死为所有剧本通用字段。


==================================================
七、通用数值系统
==================================================

实现：

StatDefinition

剧本可以自己定义人物数值。


例如大曜女帝：

relationshipStats:

trust:
  min: 0
  max: 100
  displayName: 信任

affection:
  min: 0
  max: 100
  displayName: 好感


其他剧本可能定义：

respect
fear
hostility
loyalty
sanity


世界状态同理。

当前：

威望
民心
军权
朝局稳定
财政

迁移为：

WorldStatDefinition[]

而不是固定数据库字段。


数据库保存：

statKey
value

而不是：

prestige
publicSupport
militaryControl
...


==================================================
八、关系触发规则剧本化
==================================================

“大曜女帝”中的：

好感 > 70
信任 > 80 && 好感 > 60
两人好感 > 60
冷落三次
破例三次

不得作为整个软件通用规则。


它们应该迁移至：

dayao_empress/rules.json


例如：

{
  "trigger": {
    "all": [
      {
        "stat": "trust",
        "operator": ">",
        "value": 80
      },
      {
        "stat": "affection",
        "operator": ">",
        "value": 60
      }
    ]
  },
  "eventType": "vulnerability_event"
}


Engine 提供通用：

Rule Evaluator

但具体规则来自 Scenario Package。


==================================================
九、规则采用声明式，不允许导入任意代码
==================================================

这是安全要求。

Scenario Package：

只能包含：

JSON
Markdown
图片
受支持的数据文件

不能包含：

.js
.ts
可执行脚本
shell
SQL
任意服务器代码


规则系统使用：

安全的 Declarative Rule Schema

不要允许用户导入 JS：

eval(...)
new Function(...)
动态 require

禁止剧本包执行任意服务器代码。

十、世界背景
==================================================

- 政治制度

==================================================
十一、Lore 系统
==================================================

建立通用 LoreEntry：

title
content

Prompt Builder 不要每回合把全部 Lore 发送给模型。

- 当前人物
- 地点

- 当前剧情

检索相关 Lore。


==================================================
十二、开局系统
==================================================

opening.md

负责固定开场。


允许声明：

openingMode:

fixed
generated_from_seed
interactive_setup


fixed：

直接显示作者写好的序章。


generated_from_seed：

模型根据剧本开局条件生成第一幕。


interactive_setup：

先询问玩家：

姓名
身份
背景
开局选择

然后开始故事。


“大曜女帝”继续使用：

fixed opening。


==================================================
十三、固定序章授权
==================================================

如果 opening.md 中包含：

玩家角色动作
玩家心理
玩家对白

这些内容视为：

作者预先授权的既定开场。

开场结束以后恢复 PlayerOwnershipPolicy。


==================================================
十四、叙事风格
==================================================

- 人称
- 文风
- 正文长度
- 对话比例
- 环境描写强度
- 是否偏小说
- 是否偏聊天
- 恋爱节奏
- 暴力描写程度
- 是否使用状态栏
- 是否显示选项


例如大曜女帝：

核心为：

正经剧情
公事推动关系
慢热
不全员倒贴
人物保持独立动机


这些属于 Scenario Style，
不应写死在 Engine。

==================================================
二十一、存档绑定剧本版本
==================================================

重要：

旧存档应继续使用：

==================================================

如果剧本：

1.1

==================================================
二十三、动态人物仍然保留
==================================================

两者都使用：

区别：

Seed Character：

Dynamic Character：
剧情运行中出现。


不能因为通用化而取消动态人物功能。


==================================================

最终原则
==================================================

最终产品不应是：

“把大曜的文字替换掉，
就假装支持其他世界。”

而应该是真正的数据驱动互动小说引擎。


Engine 管：

- AI 调用
- 人物
- 记忆
- 状态
- 分支
- 历史
- 存档
- 动态人物
- 规则执行
- 手机 UI
- 公网运行


Scenario Package 管：

- 谁是玩家
- 世界是什么
- 有哪些初始人物
- 人物是什么性格
- 开局是什么
- 有哪些数值
- 有哪些规则
- 时间如何计算
- 什么文风
- 有哪些 Lore


Save 管：

“这一局实际发生了什么。”


必须严格区分：

Engine
Scenario
Save


这是此次通用化改造最核心的架构要求。
